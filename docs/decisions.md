# Журнал решений (ADR)

Хронологический список принятых решений с обоснованием. Формат: **что решили — почему —
следствия**. Прежде чем оспаривать выбор, читай запись здесь.

---

## Зафиксировано до этого документа (из архитектуры v2.0)

- **Realtime — Centrifugo, не самописный.** Каналы, presence, history, JWT, WS-фолбэк,
  масштабирование через Redis из коробки. Писать руками — главная потенциальная ошибка.
- **Уведомления только внутри сайта на первом релизе.** Тост / центр уведомлений / Web Push.
  Место под Telegram-бота оставлено (абстрактные каналы доставки), но в релиз не входит.
- **Русская локализация в схеме БД** (`name_ru`, `message_ru`), не в файле переводов на фронте.
  Это ядро ценности продукта (особенно сообщения рейс-контроля).
- **Палитра «Оксид».** Бордовая подложка, интерфейс без цветного акцента, цвет только в данных.
  См. [design-system.md](design-system.md).
- **Правовые вопросы решены силами юристов заказчика.** В архитектуре не рассматриваются.

## ADR-001. Провайдер данных за интерфейсом `DataProvider`
**Решение.** Все источники (OpenF1, Jolpica, FastF1) прячутся за Protocol `DataProvider`.
**Почему.** Смена/добавление источника = один класс, а не переделка. Снижает связанность с
коммерческим тарифом OpenF1.
**Следствия.** MVP использует `JolpicaProvider` (бесплатный, без ключа) для расписания;
`OpenF1Provider` подключается в Фазе 3 для live.

## ADR-002. Стек подтверждён без изменений
**Решение.** Next.js + FastAPI + Postgres/TimescaleDB + Redis + Centrifugo + uPlot + Docker.
**Почему.** Внутренне согласован, без оверинжиниринга для масштаба 5–10k одновременных зрителей.
Разбор — в [stack-review.md](stack-review.md).
**Следствия.** Приняты 4 оговорки (ADR-003…006).

## ADR-003. Postgres выносится на отдельный узел / больше RAM
**Решение.** БД не делит VPS с API. Минимум 16 ГБ RAM под узел БД в проде.
**Почему.** TimescaleDB любит RAM под кэш гипертаблиц; во время live добавляется burst-запись
из ingest. Узел БД «прижмёт» раньше Centrifugo.
**Следствия.** В `docker-compose.yml` (dev) всё в одной сети для простоты; в проде БД —
отдельная машина. Отражено в [deploy.md](deploy.md).

## ADR-004. Фоновые задачи — ARQ, не Celery
**Решение.** ARQ.
**Почему.** Тот же event loop и Redis, что и у asyncio-стека; без тяжёлого billiard-слоя Celery.
Сложные workflow/routing в профиле нагрузки не требуются.
**Следствия.** Развилка «ARQ или Celery» закрыта. Вводится вместе с ingest (Фаза 3).

## ADR-005. `pandas` не в request-path
**Решение.** Ни одного вызова pandas в синхронном обработчике REST. Тяжёлые расчёты
(деградация шин, дельты, темп на топливе) — только в post-session воркере, результат в БД.
**Почему.** Один расчёт на лету убивает p99.
**Следствия.** Жёсткое правило в `apps/api`. Продублировано в [CLAUDE.md](../CLAUDE.md).

## ADR-006. `packages/contracts` — единый источник правды с автогенерацией
**Решение.** Типы фронта и бэка синхронизируются автоматически, не руками. Механика:
FastAPI отдаёт OpenAPI → генерация TS-типов для web.
**Почему.** «Единый источник» руками разъезжается на второй месяц.
**Следствия.** В MVP типы заведены вручную минимально; автоген из OpenAPI вводится в Фазе 2,
когда стабилизируется контракт результатов.

## ADR-007. Видео — всегда отдельный сервис, на старте только embed
**Решение.** На первых фазах — embed сторонних платформ (Twitch/VK Video/YouTube) +
регулятор смещения звука. Собственный хостинг не строится. Если понадобится: VOD — своими
силами отдельным сервисом `/apps/video`; live — через управляемый сервис (Kinescope/VK Video
в РФ; Mux/api.video за рубежом), не свой пайплайн.
**Почему.** Стек к видео отношения не имеет; главная статья — не серверы, а CDN-egress
(≈2.7 ТБ за одну гонку при 1000 зрителей 720p) и live-транскодинг. Регулятор смещения —
настоящая фича, и он не требует ни байта видеохранилища.
**Следствия.** Плеер (UI) — на основном стеке и в стиле «Оксид»; конвейер — снаружи.
Подробно — [video-strategy.md](video-strategy.md).

## ADR-008. MVP = Фаза 1 (Расписание), запускается через Docker Compose
**Решение.** Первый рабочий срез — расписание сезона, страницы этапов, время в часовом поясе
пользователя, обратный отсчёт. Гостю доступно без регистрации. Запуск `docker compose up`.
**Почему.** Каждая фаза даёт работающий продукт; расписание — фундамент SEO-трафика.
**Следствия.** Реализовано: `postgres`+`redis`+`api`+`web`. Уведомления/чат/live — дальше.

## ADR-009. Название и домен — race.live
**Решение.** Бренд и домен проекта — **race.live** (доменный хак: домен читается как имя
«race live»). Вордмарк в интерфейсе — `race.live` строчными, `.live` приглушён `--mute`.
**Почему.** Мгновенное массовое узнавание («живые гонки»), точное попадание в суть продукта
(живой тайминг + стримы), короткое имя-вордмарк в духе twitch.tv. Домен свободен (RDAP),
приобретён за ~3500 ₽. Нет коллизии с ВК-сообществом «Racecast» (рассматривалось и отклонено:
и коллизия в нише кастеров, и занятые `.ru`/`.com`).
**Следствия.** `.ru`/`.com` заняты другими — бренд держится на `.live` (как twitch.tv). Учесть
ложного друга: кириллическое «рейс» = авиарейс; аудитория читает англ. «race», контекст снимает.
Имя обновлено в `apps/web` (вордмарк, метаданные), `apps/api` (title), docker-compose
(`name: racelive`) и документации.
