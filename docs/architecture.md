# Архитектура

Версия 2.0. Этот файл — рабочая копия архитектуры для разработки. Продуктовое видение
и обоснования — в [decisions.md](decisions.md).

## Общая схема

```
              ВНЕШНИЕ ИСТОЧНИКИ
   OpenF1 (live+telemetry, Фаза 3) · Jolpica (расписание/результаты, MVP) · FastF1 (бэкфилл)
                        │
                        ▼
            ┌───────────────────────┐
            │    INGEST WORKERS     │  только спортивные данные, без ПДн
            │ scheduler/live/post   │  (Фаза 3; в MVP расписание тянет сам API)
            └───────────┬───────────┘
                        │
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
    ┌─────────┐   ┌───────────┐   ┌────────────┐
    │  REDIS  │   │ POSTGRES  │   │ CENTRIFUGO │
    │ hot/pub │   │+Timescale │   │ WS fanout  │  (Фаза 3)
    └────┬────┘   └─────┬─────┘   └─────┬──────┘
         └──────────────┼───────────────┘
                        ▼
              ┌──────────────────┐

        ┌─────────┐         ┌─────────┐

        └─────────┘
```

## Компоненты

### apps/api — FastAPI
REST + BFF, авторизация (Фаза 3), слой провайдеров, кэш. **Ни один публичный ответ не
возвращает сырой объект провайдера** — всё проходит через `app/schemas.py`. Клиент провайдера
обёрнут в token-bucket (`app/ratelimit.py`). В MVP API сам тянет и кэширует расписание;
в Фазе 3 live-данные приходят от ingest-воркеров.

Слой провайдера — за интерфейсом `DataProvider` (`app/providers/base.py`). Реализации:
- `JolpicaProvider` — расписание/результаты, бесплатно, MVP по умолчанию.
- `OpenF1Provider` — live + телеметрия, коммерческий тариф (Фаза 3).
- `FastF1Provider` — историческая аналитика, бэкфилл до 2023 (Фаза 4+).

### apps/ingest — Python + asyncio (Фаза 3)
scheduler (календарь раз в сутки; поднимает live-воркер за 30 мин до сессии), live-воркер
(поток → нормализация → Redis + батчи в Postgres → дельты в Centrifugo), post-session
(добивка пропусков, производные метрики, `is_final`). Обязательны: идемпотентность
(ключ `(session_id, driver_id, ts)`, `ON CONFLICT DO NOTHING`), буфер реплея (снапшот из
Redis при подключении), деградация при обрыве источника.

### apps/events — Python (Фаза 3)
Доменное событие → решает, кого касается → шлёт в каналы Centrifugo. Каналы доставки
абстрактны (`ToastChannel`/`CenterChannel`/`PushChannel`; `TelegramChannel` — позже одним классом).
Дедупликация по `(user_id, event_id)` в Redis, TTL сутки.

### Realtime — Centrifugo (Фаза 3)
Каналы: `timing:{session}`, `telemetry:{session}:{driver}` (по подписке), `racecontrol:{session}`,
`chat:*`, `notify:user:{id}`, `notify:global`. Телеметрия — отдельными каналами по подписке
(не гнать всем 20 машин по 4 Гц).

### apps/web — Next.js (App Router, TS, Tailwind)
SSR/ISR для SEO на расписании и результатах. Гостевой режим полноценный. Дизайн-система «Оксид»
(см. [design-system.md](design-system.md)). В MVP серверные компоненты берут данные из API по
внутреннему URL (`API_INTERNAL_URL`), CORS для клиента настроен на будущее.

### apps/admin — Next.js (Фаза 5)
Панель модерации/контента: отключение стрима (`is_active`, эффект <5 c), мьют/удаление
сообщений из интерфейса.

## Хранилища

- **PostgreSQL 16 + TimescaleDB** — история + телеметрия (hypertable). Пользовательская БД
  хранится в РФ; ingest-воркеры (спортивные данные, без ПДн) — отдельно, вне РФ.
- **Redis** — hot state, pub/sub, дедуп уведомлений, кэш.
- **Centrifugo** — WS-фанаут (Фаза 3).

## MVP-срез (что реально работает сейчас)

`postgres` + `redis` + `api` + `web` в docker-compose. Поток: web (RSC) → api `/api/v1/*` →
кэш в Postgres → при промахе `JolpicaProvider` (за token-bucket) → upsert в Postgres.
Centrifugo/ingest/events поднимаются в Фазе 3.

## Правовой контур в коде

- `<DataAttribution />` на каждой странице с данными провайдера.
- Нет публичного проксирования сырых данных (только сериализаторы/агрегаты).
- Token-bucket на клиенте провайдера — лимит не превышается физически.
- Историческая сессия тянется один раз, метится `is_final`, больше не запрашивается.
